# Checkout Session - User Stories and Business Rules (feature 33)

Phase 1 BA · Realized by `docs/02-architecture-techlead/33-checkout-session/`. Kernel rules (registry, no-default, error catalog) live in `docs/01-requirements-ba/32-monetize-overview/` and are consumed, never re-decided.

## User stories

| Story ID | As a | I want to | So that | Priority |
|---|---|---|---|---|
| US-01 | Buyer | preview the exact charge, pay once, and return to a clear pending/success/failure state | double-submit, expiry, and return behavior are identical on every rail | Must |
| US-02 | Frontend checkout | quote without creating rows, create idempotently, and poll one status shape | I follow the single buyer journey from price intent to a tracked pending order | Must |
| US-03 | Support/ops | look up an order by `orderCode` and cancel stuck pendings | I explain expiry without ambiguity | Must |
| US-04 | Ops | enable/disable rails and tune display order without deploys | I can answer "why isn't X offered" from config + capability rules | Must |
| US-05 | Release/QA | see identical idempotency, expiry, cancel, and return drills pass per rail | breadth never outruns shared-contract conformance | Must |

## Business rules

- BR-01 Quote before create: `POST /api/v1/billing/quote {plan? | productId?, provider?, couponCode?}` returns `{amountVnd, provider?, eligibleMethods[], catalogVersion, quoteToken, expiresAt}` with zero side effects. Pricing recomputed server-side from the plan catalog (35; in-service - active term rows, explicit `term`) or shop's `checkout-context` (price frozen at create per 22) minus a validated coupon; client amounts are ignored. `quoteToken` validity is 15 min.
- BR-02 Quote-charged identity: quote amount equals created `amountVnd` to the VND across plan/product × provider × coupon cells; the fee snapshot `{grossVnd, feeLines[], netVnd, rateVersion}` is pinned at create from shop's internal fee quote and is immutable; any drift detected at create (token present) refuses with 409 `amount_changed` — a different amount is never charged.
- BR-03 Create (idempotent, explicit): `POST /api/v1/billing/checkout {provider, plan? | productId?, term?, buyerEmail?, couponCode?, returnUrl?, cancelUrl?, shipTo?, extras?, quoteToken?}` + optional `Idempotency-Key` header. `provider` is required (omitted/unknown → 422 with the eligible list); eligibility (plan/product × provider matrix ∩ kill-switch survivors) is validated server-side before any row; then one `orders` row: non-sequential int64 `orderCode` UNIQUE, `amountVnd INT`, `status=pending`, immutable `provider`, `expiresAt` from per-rail TTL, `kind` denormalized from the catalog context (`plan`, `merch`, `course`, `service`, `tip`, ...).
- BR-04 Idempotency: same key + same fingerprint (over intent, provider, amount, return/cancel URLs) → one row and the same handoff re-issued; same key + different fingerprint → 422 `idempotency_key_reuse`; keyless double-click collapses within the 90 s fingerprint window (cache-held, never a row).
- BR-05 Validation (fail closed): unknown plan/product → 404 `product_absent` / `plan_not_found`; plan intent with missing/invalid `term` → 422 `term_required`/`term_invalid`; `free` plan intent → 422 `plan_not_purchasable`; no active term row → 409 `plan_not_published`; non-live product → 409 `product_not_live`; fee schedule unpublished → 409 `schedule_not_published`; ineligible provider → 422; invalid/expired coupon → 422; malformed `buyerEmail` or missing email for guests → 422 `email_required`; off-allowlist `returnUrl`/`cancelUrl` → 422 `return_url_invalid`; missing ship-to for `merch` → 422 `ship_to_required`; responses never leak catalog internals.
- BR-06 Handoff: create returns `next {kind: url|qr|sheet|token, payload}`; a handoff build failure leaves the order `pending` and returns 502 `handoff_failed` (retryable); return/cancel URLs must be same-origin under `/app/billing/{return,cancel}` carrying only `orderCode` — validated at create, never at redirect time.
- BR-07 Expiry: every pending order carries `expiresAt` (per-rail config); the sweep flips `pending|authorizing → expired` exactly once (rerun is a no-op); expired orders render the expired UX and accept only cancel-then-new-checkout; late money against `expired|cancelled` is rejected and logged per the uniform late-event rule (34 enforces at grant).
- BR-08 Cancel: `POST /api/v1/billing/orders/{orderCode}/cancel` (owner-scoped) moves `pending → cancelled` once (`authorizing` orders resolve by capture outcome or expiry — 34's matrix; never by cancel); already-cancelled → 200 idempotent; any other state → 409 `cancel_conflict`; cancel-then-new-checkout is the only way to switch providers mid-intent; grant racing cancel resolves per 34's legal edges.
- BR-09 Return handling: provider redirects land on `/app/billing/pending/{orderCode}`, which polls `GET /api/v1/billing/orders/{orderCode}` (34) and renders the canonical status; return pages and query params transition nothing — a forged `?status=paid` changes no row.
- BR-10 Selection surface: the eligible set = registry ∩ eligibility matrix ∩ kill-switch survivors ∩ capability filter (server-side); `GET /api/v1/billing/payment-methods` returns per member `{provider, displayName, handoffKind, disabledReason?}` in ops-config display order, or a stable API order rendered verbatim when config is absent; no code-level favorite exists (grep-gated).
- BR-11 Guest policy: plans require login; products (incl. tips) allow sessionless buyers with mandatory `buyerEmail`. Guest rows carry a claim-bound `user_id` (`guest:` + HMAC pepper of the lowercased email) — no null-owner rows; the raw email is stored RLS-protected, masked in logs, and scrubbed on deletion; no account is created and no claim/transfer machinery exists; the receipt is emailed at grant, and the read-only magic-link receipt view is owned by 37.
- BR-12 Data minimization: `shipTo` stored for `merch` only (name, phone, address; never logged, never returned in list views, carried through `order.granted.v1`); `extras` is a bounded scalar map (`bookingId` etc. per consuming feature), stored once and evented.
- BR-13 Lead opt-in: consent is an explicit unchecked-by-default checkbox; on opt-in the checkout writes a lead via `POST /internal/v1/leads` with `source=checkout`, `sourceRef=orderCode`, same consent semantics as 27 (consent recorded at capture); the write is post-commit, best-effort with bounded retry, and never blocks or fails the order.
- BR-14 Abuse: Turnstile on anonymous surfaces; quote/create/cancel under the platform rate envelopes (32); rapid bursts throttled with `throttled` 429; idempotency keys bounded in length and rate.
- BR-15 Audit: create, handoff issuance, expiry flip, cancel, and guest-id minting append `audit_log` rows; support traces any session by `orderCode`.
- BR-16 Transition authority: only a verified provider confirmation (34) or a sweep transitions an order; webhooks, return pages, query params, and support reads never transition; cron paths shares that authority (33's sweep) explicitly.
