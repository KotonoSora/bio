# Order Status and Orchestration - User Stories and Business Rules (feature 34)

Phase 1 BA · Realized by `docs/02-architecture-techlead/34-order-status-and-orchestration/`. Kernel rules (status vocabulary BR-04, conformance, error catalog) live in `docs/01-requirements-ba/32-monetize-overview/`, checkout rules in `docs/01-requirements-ba/33-checkout-session/` — consumed, never re-decided.

## User stories

| Story ID | As a | I want to | So that | Priority |
|---|---|---|---|---|
| US-01 | Provider grant/sweep/ops handler | transition orders only along legal edges through one guard | every rail shares one canonical lifecycle | Must |
| US-02 | Buyer | see one consistent status vocabulary and the right next action on pending, history, and detail | money never feels ambiguous or jargon-laden | Must |
| US-03 | Support/ops | read any order and know precisely what can still happen to it | I explain state without reconstructing provider dashboards | Must |
| US-04 | Shop registrar (23/24/25) | receive durable, deduplicated grant events | fulfillment/enrollment/booking starts exactly once | Must |
| US-05 | Release/QA | see edge-matrix, late-event, and replay drills pass per rail | breadth never outruns conformance | Must |

## Business rules

- BR-01 Canonical lifecycle: the closed nine-value set of 32 BR-04 (`pending | authorizing | paid | failed | cancelled | expired | refunded | disputed | chargeback_reversed`) is the only order vocabulary; the `orders.status` CHECK mirrors it exactly and both drift checks fail review. Every buyer read projects `{status, status_detail}`; provider-native codes (VNPay response codes, ZaloPay query results, Stripe intent states, rail sync notes) never surface to buyers, logs, events, or other services.
- BR-02 Legal edges: `pending → authorizing|paid|failed|cancelled|expired`; `authorizing → paid|failed|expired`; `paid → refunded|disputed`; `disputed → paid|chargeback_reversed`. Every other edge is refused in code and in conformance tests; terminal values never re-enter `pending|authorizing` (`paid` moves only toward refund/dispute).
- BR-03 Actor authority: `→ paid` only via verified provider confirmations (webhook/callback/IPN/query/sweep verify) through the amount-checked atomic grant; `→ cancelled` only via 33's owner/ops cancel (pending only) or a provider-side cancel mirrored by its lifecycle handler before money movement; `→ expired` only via sweeps (33's expiry; 40's settlement); `→ failed` via verified decline or settlement; `→ refunded|disputed|chargeback_reversed` only via settlement handlers (38/40). Buyer clients and return pages transition nothing — they poll and render.
- BR-04 Grant step: a verified confirmation resolves its order by provider reference/`orderCode`, checks the reported amount against stored `amount_vnd` (mismatch: no grant, confirmation quarantined to ops with evidence, the order lands `failed` via the rail settlement sweep per 32's exception catalog), then applies the transition + audit + `psp_ref` first-write in one transaction. Failure transitions carry buyer-safe reasons into `status_detail` only.
- BR-05 Replay safety: redelivered confirmations are success-without-effect via the terminal fast-path; double webhook + settlement sweep races yield one grant and one audit chain. The V6 `provider_events` table (40) stores the UNIQUE anti-replay keys (`orderCode` + provider event id); the guard consumes them, never re-stores.
- BR-06 Late money: confirmations for `cancelled|expired` orders are refused and logged (`transition.late`; ops alert at ≥ 5 in 60 min per rail); only the audited bank-rail exception flows (40, `ROLE_OPS` + mandatory reason) may re-link; card captures landing after cancel route to that rail's settlement refund path — never granted, never silently dropped.
- BR-07 Grant event: on grant, `order.granted.v1` (frozen shape, 32 TL 03) emits post-commit to `billing.events`; at-least-once with consumer dedupe (23/24/25); bounded retry then `billing.events.dlq` + alert; a reconciliation re-emits recent paid grants lacking an emitted marker; ledger/receipt effects visible ≤ 60 s p95 (32 NFR-02); grants never wait on sends.
- BR-08 Order reads: `GET /api/v1/billing/orders` (owner, cursor page, newest first, optional `status` filter) and `GET /api/v1/billing/orders/{orderCode}` (owner; support reads via 32's trace) return the canonical projection; the detail adds lines, provider display name, a `merch`-only fulfillment block from 23 (status fields only — `pending_print|printing|shipped|delivered|failed|cancelled`; ship-to never crosses) and the receipt link (37) when `paid` or later. Reads never transition; foreign order → 403 + RLS deny; absent → 404.
- BR-09 Status detail: `status_detail` is a server-composed human string (vi/en) rendered verbatim; clients hold no code dictionary and never template copy from codes; state-driven actions come from the fixed map (BA 04).
- BR-10 Disputes: `disputed` freezes buyer actions (support contact only) and flags entitlements per the plans/shop dispute rule; win restores `paid`, loss moves `chargeback_reversed`; entitlement freeze/revoke execution and period math are 35's ledger domain (forward seam); edges fire only from verified settlement events (40).
- BR-11 Native-state mapping: each rail's native states map onto the canonical set in code tables owned by its adapter (40); non-terminal native states transition nothing; the 8×N conformance matrix is green before any rail change ships, with results recorded per release. A new state or edge is added in this feature first or not at all.
- BR-12 Killed rails: a killed rail's in-flight pendings settle via its verification/sweep path or expire; they are never auto-migrated to another rail (re-price and re-consent would be implicit) and never silently dropped (buyer messaging per 32's catalog).
- BR-13 Audit: every transition appends `audit_log{actor, action, target=orderCode, detail={from,to,eventId,rail}, at}` inside the transition transaction; the per-order trail is replayable for support (32's trace route); secrets/signatures redacted; retention 24 months.
- BR-14 Delete guard: `GET /internal/v1/orders/has-product-orders/{productId}` returns `{exists}` = any `orders` row referencing the product (any status); service-JWT only; bounded by the platform statement timeout; powers 22's `product_has_orders` 409 / `orders_check_unavailable` 503 semantics without cross-service table reads.
