# Link Blocks Frontend Plan (editor UI + API integration — UI build steps)

PLAN ref: P1b-2 (dashboard CRUD, drag-order, sizes, carousel, thumbnails). BA source: `docs/link-to-bio/blocks/link-blocks.md`. Server truth in `docs/link-to-bio/blocks/link-blocks-backend-plan.md` (schemas, codes, ordering rule — never redefined here).

## Purpose

Give the frontend developer an ordered UI procedure for the block editor: list screen, per-type forms, drag-reorder with rollback, scheduling inputs, and the exact integration sequence per action. Follow steps 1–7 in order. The server validates everything; the client mirrors schemas for instant feedback only.

## Users

- Frontend developer: builds `/app/blocks` (or the profile-editor tab) against the backend plan's contracts.
- QA: executes the click-path and rollback drills.
- Creator: adds, edits, reorders, hides, and schedules blocks with immediate, honest feedback.

## Functional requirements

1. Screen and state: `/app/blocks?profile=` (owner-only) renders the ordered list (thumbnail, title, type chip, `hiddenReason` chip, overflow menu: edit/duplicate/hide/delete). Client state: `blocks[]` in server order + `pendingOp` map (per-row spinner). A `BlockSchema.ts` mirrors the backend validator (13 types, per-type fields, `https:` rule, length caps) — generated by hand from the backend plan and re-checked whenever it changes; divergence is a bug, resolved in favor of the server.
2. Step 1 — list/load flow: mount → `GET /api/v1/blocks?profile_id=` → render rows in `position` order with status chips (`scheduled_future` shows the from-date, `expired` the until-date). `403` → re-login. Empty profile → illustrated empty state with `Add block` entry.
3. Step 2 — create flow: `Add block` → type picker (13 frozen options, no free-text type) → per-type form (link: URL + title + size segmented control + thumbnail slot; social: network select + URL; embed: provider + URL with `renderer decides markup` hint; resume: document picker returning `documentId`; schedule section: visible toggle + optional from/until datetime inputs validated `until > from` before send) → `POST /api/v1/blocks` → `201` appends at end with toast → `422` maps code to field (`bad_url_scheme` under URL with `must start with https://`, `title_too_long` with counter). Non-`https:` URLs are blocked pre-send AND server-rejected — both layers, same message.
4. Step 3 — edit flow: row menu → edit dialog prefilled → `PATCH /api/v1/blocks/:id` (partial body of changed fields only) → `200` merges into list → `422` field-mapped. Type is never changeable after create (dialog hides it; attempting otherwise is a delete + create, stated in-UI).
5. Step 4 — reorder flow (the consistency-critical path): drag → optimistic list move instantly → drop commits `POST reorder {profileId, ids}` → `200` confirms (silent) → any `422` (stale list, foreign id) rolls the list back to the pre-drag order and toasts the code with a `Reload` action. While a reorder is pending, further drags queue behind it (no parallel commits). Reload at any point must show identical order — the server sequence is the truth, the client never persists positions locally.
6. Step 5 — hide/delete/duplicate flow: hide toggles `isVisible` via `PATCH` with instant chip flip + rollback on failure; delete asks confirm (names the block) → `DELETE` → row animates out, toast offers `Undo` for 5s (undo = re-`POST` the cached payload, a new row — stated honestly, not a true undelete); duplicate → `POST` copy payload → new row inserted below source (position comes back from server, client does not compute it).
7. Step 6 — schedule UX: from/until pickers show the effective public state live (`Visible now` / `Goes live Tue 9:00` / `Expired`) computed client-side from the same rule the server enforces; expired rows sink to a collapsed `Out of window` section, never deleted silently.

## Data / API touches

- Screen → endpoint map: list → `GET /api/v1/blocks?profile_id=`; create → `POST /api/v1/blocks`; edit/hide → `PATCH /api/v1/blocks/:id`; remove → `DELETE /api/v1/blocks/:id`; reorder → `POST /api/v1/blocks/reorder`. All with session cookie + CSRF; non-2xx parsed as problem JSON.
- Type mirror: `Block {id, type: 13-union, position, payload: per-type, isVisible, hiddenReason}`. Code → UI map: `unknown_block_type` ( picker prevents; direct-API only), `bad_url_scheme`, `title_too_long`, `payload_too_long`, `bad_schedule_window` → schedule section, `block_not_found` → row dropped + reload, `403` → re-login.
- Integration rule: the client sends full ordered `ids` on every reorder (server validates set-equality); the client never assigns `position` values — positions arrive from the server only.

## Acceptance criteria

- Create drill: each of the 13 types creates with correct payload; `http:` URL blocked pre-send with the exact hint, and server `422` mapped if forced.
- Reorder drill: drag 10 rows rapidly → single final commit wins, reload matches; forced stale commit rolls back with `Reload` action.
- Schedule drill: future block shows `Goes live …` and is absent publicly; expired sinks to `Out of window`.
- Delete drill: confirm names the block; Undo within 5s restores as a new row.
- Security drill: no `user_id` in bodies; type union frozen (grep for free-text type).
